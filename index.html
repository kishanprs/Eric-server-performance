Eric System — Slowdown Investigation

What happened, what we've confirmed, and what's still being fixed — for Switched On stakeholders

Updated through 29 Jul (partial) — dotted numbers show more detail on hover

Bottom line

The slowdown was caused by a filter introduced in the 19 Jul enhancement that made two screens — Charge Work and Docs — run far more database lookups than before, each one slower too. That's confirmed and reproduced independently on both regional servers.

On 28 Jul we switched the filter off for everyone except Switched On (KO) customer logins, as a temporary measure. That fixed the Docs tab for everyone except KO customers, who still have the filter on and are still visibly slower there — expected, and will be resolved once the filter itself is fixed.

The Charge Work tab is more complicated: the workaround cut the overload, but afternoon data on the 28th uncovered a second, separate problem — several trade accounts colliding with each other on the same records, causing sharp multi-second freezes independent of KO or the filter. That still needs a fix from Digital Fusion.

Hardware, image upload size, and folder structure have all been ruled out as causes. The hardware upgrade completed 29 Jul (DB servers now 16 cores/32GB, web servers 8 cores/16GB), and it proves the point: KO customers — who still have the filter on — got barely any faster despite 4x the CPU and 2x the RAM. That confirms this was never a hardware problem, and turning the filter back on for everyone would very likely still be slow.

The two problem screens, where they stand today

Docs tab

KO customers still slow — as expected

Caused by the new filter running far more lookups than it needs to. Switching the filter off for everyone except KO customers fixed this tab immediately for all trade and staff users.

~2xslower for KO than everyone else, afternoon of 28 Jul
0impact on non-KO users — fully resolved for them

KO customers still have the filter switched on, so this is exactly what we'd expect — not a new problem. Fixed once the filter logic itself is corrected and safely re-enabled.

Charge Work tab

Partially improved — new issue found

The filter-removal workaround cut overall load 4–7x. But afternoon logs on the 28th show several trade accounts periodically colliding with each other on the same records, causing sudden multi-second (occasionally 20–30 second) freezes — unrelated to KO or the filter.

7trade accounts caught in one contention cluster, one server, one morning
up to 30ssingle freeze during a collision

This explains why field reports of "back to normal" and ongoing complaints can both be true — it's fine most of the time, with sharp, unpredictable freezes when two people hit the same record. Needs its own fix from Digital Fusion, most likely around how tightly Charge Work locks records during editing.

Confirmed with a full 24-hour read of the 28th: the freezing is a business-hours phenomenon. By evening, once fewer trades are working concurrently, Charge Work drops to single-digit milliseconds for everyone — which is exactly why some field reports say "fine" while the daytime data still shows real problems.

Would turning the filter back on for everyone still be slow? Yes, most likely — and now we have direct evidence, not just a guess.

KO customers still have the original filter switched on, so comparing their speed before vs. after the hardware upgrade isolates the hardware effect specifically — same query logic, dramatically more CPU and RAM. If they'd sped up close to as much as the CPU/RAM did (4x and 2x), that would point at hardware as the real constraint. Instead KO improved only 0–22% and remains 3–8x slower than desktop users doing the same thing. That means the cost is baked into the query itself, not how much compute is behind it — so re-enabling the filter for everyone would spread that same expensive query across a much bigger group of users, not fix it. Recommend holding off until Digital Fusion's fix to the filter logic actually lands.

Also found

Nightly cleanup job has slowed down significantly

A routine overnight "Purge Old Alerts" job now takes several minutes instead of seconds, every night, on both servers. Separate issue, needs its own fix — not urgent, but worth Digital Fusion's attention.

Disk-activity lead: confirmed unaffected by the hardware upgrade

A separate performance capture taken closer to the 19 Jul release showed disk activity on R7's database server much higher than a capture taken a couple of days later — CPU and RAM looked consistent between the two, so this looked disk-specific. Post-upgrade data now confirms it: disk activity stayed essentially the same before and after the hardware upgrade, exactly as expected since more CPU/RAM doesn't touch disk I/O. Still unexplained and still worth investigating — just now ruled out as something the hardware fix would ever have solved.

Brief server-wide pause, ten minutes past every hour

A short pause affecting all screens at once has been identified around :10 past each hour, caused by a backup script that Digital Fusion runs — separate from CCL's regular overnight backup. A full-day read now shows this pattern 3 separate times on each server, reinforcing it's real and periodic rather than a one-off. It briefly touches every user, not just Charge Work or Docs, so it's going on Digital Fusion's list to explain and, if possible, streamline.

Ruled out

Photo storage isn't a bottleneck

Each new work order gets its own folder, so concurrent uploads from different trades don't collide with each other on disk.

Worth noting: if you browse that folder in Windows Explorer it can feel slow to open — that's Explorer having to read every folder just to list them (there are millions of files total). It doesn't mean FileMaker is slow there: FileMaker already knows the exact folder name it needs (the WO number) and goes straight to it, the same way you'd drive straight to a known address instead of checking every house on the street. The two aren't connected.

Uncompressed mobile photos aren't the cause

Upload traffic didn't actually increase after the release. Still worth compressing eventually, just not the emergency.

Hardware isn't the cause — the completed upgrade proves it

Servers aren't struggling on average, so hardware isn't why things slowed down. An upgrade completed anyway as a buffer: DB servers to 16 cores/32GB, web servers to 8 cores/16GB. This turned into a useful test: KO customers still have the filter on, so comparing their speed before and after the upgrade isolates the hardware effect. KO improved only 0–22% despite 4x the CPU and 2x the RAM — confirming this is a query-logic problem, not a resource problem, and doesn't replace the filter and locking fixes still needed from Digital Fusion.

What happens next

  1. Keep the temporary filter-off workaround in place for non-KO users. Confirmed working, buying breathing room while the real fix is built.
  2. Digital Fusion fixes the filter itself for both Docs and Charge Work, so it can go back on safely for KO customers too. This is the permanent fix for the Docs slowdown and half of the Charge Work slowdown.
    • Unindexed or unstored calculations — is the filter's search criteria built on a calculation field that can't be indexed? This forces FileMaker to check every record instead of doing a fast lookup, and would explain both the volume and the per-call slowness we measured.
    • How the filter actually runs — is it doing a real indexed Find, or filtering an already-loaded portal in memory? The two have very different cost profiles at scale, and the volume increase we measured (17–160x more finds) suggests something closer to a Find running far more often than intended.
    • How often it triggers — does it run once per user action, or on every keystroke / every layout load? This alone could explain a large part of the volume increase without anything being "broken" in the traditional sense.
    • Why Docs (147) affects desktop users too — the new filter targets mobile/WebDirect, but desktop Pro users saw a real increase in Docs load as well. Something shared (a relationship, script, or layout calculation) beyond the mobile filter itself needs explaining.
    • Load-test at production scale before re-enabling for everyone — given KO's experience barely improved with 4x the hardware, don't take "it works for one customer group" as proof it'll work for the full user base. Confirm under realistic concurrent load first.
  3. Digital Fusion investigates the Charge Work record-locking issue uncovered on the 28th. Separate from the filter — this is what's causing the sharp, unpredictable freezes between trade accounts.
    • Lock granularity — does Charge Work lock at the whole work-order level, or per line item? If several trades editing the same job collide on a work-order-level lock, that would explain the multi-second-to-30-second freezes seen between unrelated trade accounts.
  4. Ask Digital Fusion about their hourly backup script — what it does and whether its timing or duration can be tuned. It's their script, not CCL infrastructure — brief, but affects every user on the system, every hour.
  5. Check the nightly "Purge Old Alerts" job for the same kind of inefficiency as the other two.
  6. Hardware upgrade is complete — DB servers now 16 cores/32GB, web servers 8 cores/16GB (Spark, 29 Jul). Confirmed via post-upgrade data: headroom improved a lot, but KO (still filtered) only got 0–22% faster — proof this alone won't fix the filter or locking issues below.
