Eric System — Slowdown Investigation: Summary

WebDirect enhancement (19 Jul release) · R7 & R10 · plain-language version

  • Main cause: since the release, two tables (129 and 147) are getting hit with 17–80x more database lookups than before, and each lookup is 6–11x slower. This is the real reason things feel slow — for everyone, not just mobile users.
  • Not the cause: image uploads from the mobile app aren't compressed, but that's not what's making things slow right now — data confirms upload traffic didn't actually increase.
  • Not a factor: each new work order gets its own separate photo/document folder, so concurrent mobile uploads don't collide with each other.
  • Also found: a nightly cleanup job is now taking much longer than it used to, on both servers.
  • Hardware: not the cause. The two database servers could use a bit more CPU as a buffer; the web servers are fine as-is.

What we found, at a glance

Two tables are overloaded Main cause

Tables 129 and 147 went from a trickle of lookups to a flood right after the 19th — on both servers, independently. Table 129 is driven by the mobile app; table 147 is driven by desktop users, which means something in the release affected people who aren't even using the new mobile feature.

Nightly cleanup job got much slower New finding

A routine overnight job ("Purge Old Alerts") now takes several minutes instead of seconds, every night, on both servers. Separate issue from the main one — worth its own fix.

Photo storage: not a bottleneck Ruled out

Each new work order gets its own separate folder for photos/documents, so different trades uploading at the same time write to different folders and don't collide. Not a factor in the current slowdown.

Why Explorer feeling slow to browse doesn't mean FileMaker is slow: Explorer has to open and read every single folder just to display the list — with 3M+ files that's naturally sluggish. FileMaker never does that. When it needs a specific work order's documents, it already knows the exact folder name (the WO number) and goes straight to it in one step, the same way you'd go straight to a specific house on a street if you already had the address, instead of walking past every house first. The total number of files elsewhere in DOCUMENTS doesn't add any extra work to that lookup.

Image compression: not the cause Ruled out

Yes, mobile photos aren't compressed before upload — but the data shows upload traffic didn't actually go up after the release. Still worth compressing eventually, just not an emergency.

Hardware: not the cause Ruled out

The servers aren't struggling for resources on average. The two database servers occasionally max out all 4 CPU cores at once during bad moments — a small CPU bump would give breathing room, but won't fix the underlying issue. The web servers have plenty of spare capacity already.

What to do next

  1. Get Digital Fusion to look at tables 129 and 147 — specifically whether the new filter uses an unindexed/unstored field, and whether it's running far more lookups than it needs to. This is the actual fix.
  2. Check the nightly "Purge Old Alerts" job — same kind of question: is it scanning an unindexed field on a table that's grown a lot recently?
  3. Hold off on buying more hardware for now — fix the above first, then re-check. A modest CPU increase on the database servers is reasonable as a buffer, not an emergency.
Sources: FileMaker Server query/lock logs (R7 & R10, 16–24 Jul 2026), Windows Performance Monitor captures (23–24 Jul 2026), and a full folder-structure scan of the container storage on both servers. A more detailed technical writeup with all supporting figures is available on request.
